# Sensitive Data Firewall：打包与部署指南

本文按当前仓库的实际脚本，整理 Linux 与 macOS 的构建、打包、安装、升级、验收和卸载流程。命令中的路径均以仓库根目录为基准。

## 如果你现在只想在本机打开 macOS

在仓库根目录执行下面整段命令。它使用本机已经存在的 Apple Development 身份生成一个本地测试包：

~~~sh
SIGNING_IDENTITY='Apple Development: zero_plfjy@icloud.com (ZN9S86U87M)' \
DEVELOPMENT_TEAM='YSGFZUQGW6' \
LOCAL_SIGNING_ONLY=1 \
CODESIGN_TIMESTAMP=none \
scripts/macos/build-release-app.sh

open build/macos-release/Guard.app
~~~

如果 Finder 仍然提示无法打开，先执行验证命令：

~~~sh
VERIFY_SIGNING_MODE=local \
scripts/macos/verify-bundle.sh build/macos-release/Guard.app
~~~

看到 `PASS: self-contained local-signed Guard.app verified` 后，再双击或执行 `open`。本地包的位置是 `build/macos-release/Guard.app`，不是 `build/macos-release/Guard-0.1.0-arm64.zip`；zip 需要先解压。

这个本地包只能验证 UI 和 GTK 是否能启动，不能激活 Endpoint Security，也不是可公证分发包。需要真实保护功能时，继续阅读下面的“正式 Release”和“安装、激活和首次配置”。

## 先看平台状态

| 平台 | 当前交付形态 | 当前状态 | 关键限制 |
|---|---|---|---|
| Linux | 原生 systemd 安装、Arch AUR 包 | 在记录的 Arch `strict-filesystem` 主机上有 Alpha 验收记录 | 需要 root、`CAP_SYS_ADMIN`、fanotify 和 polkit |
| macOS | `Guard.app` 开发包、自包含 Release 包 | 功能完成；真实安全验收仍阻塞 | 需要 Apple Endpoint Security provisioning、FDA、正常 SIP、签名和公证凭据 |

Linux 和 macOS 是两套不同的部署边界：Linux 使用 root `guardd` + fanotify；macOS 使用 `Guard.app` + Endpoint Security system extension + authenticated XPC。不要把 Linux 的 systemd 命令套到 macOS，也不要把 macOS 的 provisioning/公证流程套到 Linux。

## 安全和操作约束

开始前请确认：

- 测试只能使用合成浏览器 profile、临时 SSH key 和临时目录；不要登记真实 Cookies、密码、session、`~/.ssh/id_*` 或现有 `SSH_AUTH_SOCK`。
- 不要通过关闭 SIP、修改 TCC 数据库或降低系统安全设置来“修复”验收失败。
- 不要以 root 编译 Rust。先由普通用户构建，再使用明确的安装命令提权。
- 仓库里的 `sensitive-data-firewall-macos-harness/` 是外部验收规范，不属于产品源码；不要提交它。
- 本项目流程不需要 Docker；本教程不启动 Docker。

## 一、通用源码构建

~~~sh
git clone https://github.com/PLFJY/sensitive-file-guard.git
cd sensitive-file-guard
cargo build --release
~~~

`cargo build --release` 会构建当前目标平台的 Release 二进制。发布前至少执行：

~~~sh
cargo fmt --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
git diff --check
~~~

macOS 阶段的验收脚本使用显式 macOS/共享 crate 列表，以避免在 macOS 主机误触 Linux-only `platform-linux`；Linux 打包则使用完整 workspace。

## 二、Linux：构建、安装和运行

### 2.1 安装依赖

| 发行版 | 构建依赖 | 运行依赖 |
|---|---|---|
| Arch | `base-devel cargo rust git gtk4 libadwaita` | `systemd polkit`；可选 `libnotify openssh` |
| Debian/Ubuntu | `build-essential cargo rustc git pkg-config libgtk-4-dev libadwaita-1-dev` | `systemd polkitd`；可选 `libnotify-bin openssh-client` |
| Fedora | `gcc make cargo rust git gtk4-devel libadwaita-devel` | `systemd polkit`；可选 `libnotify openssh-clients` |

例如 Arch：

~~~sh
sudo pacman -S --needed base-devel cargo rust git gtk4 libadwaita systemd polkit
~~~

Snap/Flatpak 浏览器不属于当前安全验收路径；应使用原生 Firefox、Firefox ESR、Chromium 或 Chrome 包，并登记 canonical executable 路径。

### 2.2 从源码安装

先以普通用户构建：

~~~sh
cargo build --release
~~~

再执行安装脚本：

~~~sh
sudo deploy/install.sh
~~~

安装脚本只安装已经生成的二进制，不会替你编译、创建配置、启用服务或启动服务。主要安装位置为：

~~~text
/usr/local/bin/guardd
/usr/local/bin/guardctl
/usr/local/bin/guard-notify
/usr/local/bin/guard-ui
/etc/systemd/system/guardd.service
/usr/local/lib/systemd/user/guard-notify.service
/usr/share/polkit-1/actions/org.guardd.policy
/var/lib/guardd                 # audit DB
/run/guardd                     # IPC socket/runtime directory
~~~

安装脚本会创建 `guardd-users` 组，并把执行 `sudo` 的用户加入该组。加入新组后必须注销并重新登录，使 supplementary groups 生效。

### 2.3 创建配置并启动服务

安装不会自动生成 `/etc/guardd/config.json`，这是有意设计：空配置不能被误报为“已保护”。先发现并审核原生浏览器：

~~~sh
guardctl browser discover
guardctl ssh suggest
~~~

生成严格模式配置：

~~~sh
sudo guardctl setup --home "$HOME"
~~~

该命令会打印候选 JSON，要求确认后才写入 `/etc/guardd/config.json`，文件权限为 `0600`，不会覆盖已有配置，也不会自动登记 SSH key。确认后启动：

~~~sh
sudo systemctl enable --now guardd
systemctl --user daemon-reload
systemctl --user enable --now guard-notify
~~~

检查状态和日志：

~~~sh
guardctl status
guardctl resources list
guardctl browsers list
guardctl events
systemctl status guardd
systemctl --user status guard-notify
journalctl -u guardd -b --no-pager
journalctl --user -u guard-notify -b --no-pager
~~~

安全验收路径应使用 `strict-filesystem`。状态必须显示 `ACTIVE`，且 required filesystem marks、classifier failures、queue overflow 和 audit drops 正常。 `conservative` 是兼容模式，保留已知的替换/拓扑窗口，不应被描述为同等级安全边界。

### 2.4 Arch AUR 可选流程

`packaging/aur/PKGBUILD` 是 VCS 包，适合 Arch 用户：

~~~sh
cd packaging/aur
makepkg -si
~~~

安装后仍需显式配置和启动：

~~~sh
sudo usermod -aG guardd-users "$USER"
# 注销并重新登录
sudo guardctl setup --home "$HOME"
sudo systemctl enable --now guardd
systemctl --user enable --now guard-notify
~~~

AUR 包也不会创建 `/etc/guardd/config.json`，不会自动启用服务。

### 2.5 Linux 更新和卸载

更新时先停止服务，以普通用户重新构建，再安装和启动：

~~~sh
sudo systemctl stop guardd
cargo build --release
sudo deploy/install.sh
sudo systemctl start guardd
systemctl --user restart guard-notify
guardctl status
~~~

卸载：

~~~sh
sudo deploy/install.sh --uninstall
~~~

卸载脚本会移除程序、unit 和 polkit policy，但保留 `/etc/guardd` 与 `/var/lib/guardd`，便于人工审查和决定是否删除。

## 三、macOS：开发包

### 3.1 环境

需要 macOS 13+、Xcode Command Line Tools、Rust、GTK4 >= 4.14、libadwaita >= 1.4。Homebrew 开发环境示例：

~~~sh
brew install rust gtk4 libadwaita pkg-config
~~~

构建开发包：

~~~sh
scripts/macos/build-dev-app.sh
scripts/macos/inspect-signing.sh
~~~

产物：

~~~text
build/macos/Guard.app
~~~

开发包可以引用 Homebrew GTK 动态库，不是可分发包，也不能证明 Endpoint Security 已激活。生命周期查询：

~~~sh
build/macos/Guard.app/Contents/MacOS/Guard --system-extension-status
build/macos/Guard.app/Contents/MacOS/Guard --activate-system-extension
build/macos/Guard.app/Contents/MacOS/Guard --deactivate-system-extension
~~~

只有 Apple 批准的 system-extension entitlement、匹配 provisioning、正确签名、用户批准和 FDA 都满足后，才可以进行真实 ES 验收。

## 四、macOS：自包含 Release 包

### 4.1 本地打包烟测

本地没有正式 provisioning 时，必须显式使用 `LOCAL_SIGNING_ONLY=1`。不要把下面的占位符原样复制；应先查看本机身份：

~~~sh
security find-identity -v -p codesigning
~~~

然后把真实的 `Apple Development: ... (TEAMID)` 和 Team ID 填入。当前记录的开发机可用值是 `Apple Development: zero_plfjy@icloud.com (ZN9S86U87M)` / `YSGFZUQGW6`。该模式会省略受限 entitlement，使 AMFI 可以启动本地 smoke 包，但它不可激活 ES、不可公证、不可分发：

~~~sh
SIGNING_IDENTITY='Apple Development: zero_plfjy@icloud.com (ZN9S86U87M)' \
DEVELOPMENT_TEAM='YSGFZUQGW6' \
LOCAL_SIGNING_ONLY=1 \
CODESIGN_TIMESTAMP=none \
scripts/macos/build-release-app.sh
~~~

验证并启动 GTK：

~~~sh
VERIFY_SIGNING_MODE=local \
scripts/macos/verify-bundle.sh build/macos-release/Guard.app

smoke_home=$(mktemp -d /tmp/guard-smoke.XXXXXX)
HOME="$smoke_home" \
  build/macos-release/Guard.app/Contents/MacOS/Guard --packaging-smoke
~~~

Release 脚本会递归收集实际使用的非系统 Mach-O 依赖、复制 GTK/GdkPixbuf 运行时资源、重写 `@rpath`/`@loader_path`、显式从内到外签名，并生成：

~~~text
build/macos-release/Guard.app
build/macos-release/Guard-<version>-arm64.zip
~~~

当前只声明 arm64。不要把本地产物称为 notarized 或 security-accepted。

### 4.2 正式 Release 打包

正式路径需要外部提供 Developer ID 或 Apple 认可的签名身份、`DEVELOPMENT_TEAM`、主 App provisioning profile 和 Endpoint Security extension provisioning profile：

~~~sh
SIGNING_IDENTITY='Developer ID Application: Example (TEAMID)' \
DEVELOPMENT_TEAM='TEAMID' \
HOST_PROVISIONING_PROFILE='/secure/Guard.provisionprofile' \
EXTENSION_PROVISIONING_PROFILE='/secure/GuardES.provisionprofile' \
GUARD_VERSION=0.1.0 \
GUARD_BUILD_NUMBER=1 \
scripts/macos/build-release-app.sh
~~~

不设置 `LOCAL_SIGNING_ONLY` 时，缺少任一 profile 会在构建前失败。正式验证模式会检查 profile 已嵌入、Host 只有 system-extension install entitlement、Extension 只有 Endpoint Security entitlement、helper 没有受限 entitlement、所有组件使用 hardened runtime。

### 4.3 公证和 Gatekeeper

公证凭据放在 Keychain profile，不要写入仓库：

~~~sh
xcrun notarytool store-credentials GuardNotary \
  --apple-id ACCOUNT \
  --team-id TEAMID \
  --password APP_SPECIFIC_PASSWORD

NOTARY_KEYCHAIN_PROFILE=GuardNotary \
scripts/macos/notarize-release.sh build/macos-release/Guard.app
~~~

脚本执行 `notarytool submit --wait`、staple、ticket validate、Gatekeeper assessment 和最终 zip 重建。没有 notary profile 时应标记 BLOCKED，不能用本地签名绕过。

## 五、macOS：安装、激活和首次配置

正式包安装到：

~~~text
/Applications/Guard.app
~~~

然后按顺序操作：

1. 启动 Guard，发起 system extension activation。
2. 若 macOS 显示待批准，在系统设置中批准；不要调用 `systemextensionsctl`。
3. 如果状态为 `REQUIRES_FULL_DISK_ACCESS`，在系统设置中给 Guard/扩展授予 FDA；Guard 不修改 TCC 数据库。
4. 在 Guard 中单独启用 pending helper；helper 状态不等于 ES 状态。
5. 配置并审核浏览器 profile/SSH key 后，再启用保护策略。
6. 只有当 XPC 可用、ES client 可连接、策略已启用且产品状态为 `ACTIVE` 时，才可报告“保护已生效”。

命令行工具位于 `/Applications/Guard.app/Contents/MacOS/guardctl`。安装不会修改 shell profile，也不会静默创建 `/usr/local/bin` 链接。

## 六、macOS：最终验收和恢复

在创建任何测试 profile 前，运行：

~~~sh
scripts/macos/preflight-final-acceptance.sh /Applications/Guard.app
~~~

预检会创建专用临时根目录，检查 SIP、签名模式、扩展生命周期、XPC enforcement health、FDA 状态和 helper 状态。平台条件不满足时退出码为 `77`，并在创建浏览器/SSH 夹具前停止。

预检通过后，才运行输出的夹具验收脚本：

~~~sh
GUARD_APP=/Applications/Guard.app \
  scripts/macos/run-browser-policy-acceptance.sh

scripts/macos/run-ssh-policy-acceptance.sh /Applications/Guard.app

GUARD_APP=/Applications/Guard.app \
  scripts/macos/run-namespace-health-acceptance.sh
~~~

这些脚本只使用临时浏览器 profile 和临时生成的 SSH key。 `guardctl ssh load` 在 macOS Alpha 中明确不支持；普通 `ssh-add` 走手动读取批准路径。

升级和恢复：

~~~sh
SIGNING_IDENTITY='Apple Development: …' DEVELOPMENT_TEAM=TEAMID \
  scripts/macos/test-release-update.sh

scripts/macos/diagnose.sh /Applications/Guard.app

GUARD_APP=/Applications/Guard.app \
  scripts/macos/uninstall-recovery.sh \
  --dry-run --preserve-data --remove-app --confirm
~~~

升级替换 App/extension，但保留：

~~~text
/Library/Application Support/Sensitive Data Firewall/config.json
/Library/Application Support/Sensitive Data Firewall/audit.db
~~~

pending operation、process graph 和临时 lease 是内存状态，不跨 extension restart/update 继承。卸载默认保留配置和审计；显式 `--remove-product-data` 只删除产品规定的配置、数据库及 SQLite sidecar，不删除浏览器 profile 或 SSH key。 `--remove-app` 使用可恢复的 Trash 移动。

## 七、常见失败的含义

| 错误/现象 | 含义和处理 |
|---|---|
| Linux `pkcheck is required` | 安装 `polkit`/`polkitd`，不要去掉 polkit 检查 |
| Linux 没有 `ACTIVE` | 检查配置是否存在、profile/key 是否存在、strict filesystem mark 是否成功 |
| macOS `HOST_PROVISIONING_PROFILE is required` | 正式 Release 缺少 profile；补充外部 profile，或明确改用 local-only 烟测 |
| macOS `No matching profile found` / AMFI kill | 受限 entitlement 与 provisioning 不匹配；不能靠重新 codesign 或 root 绕过 |
| macOS XPC 不可达 | 扩展未激活、helper 未启动、签名/Team 不匹配或 FDA/系统批准未完成 |
| macOS Gatekeeper 拒绝本地包 | Apple Development/local-only 包不是可分发公证包；执行正式签名和 notarize 流程 |
| macOS 预检退出 77 | 外部验收前置条件未满足；查看输出的具体 BLOCKED 项，不要将其改成 PASS |
| GTK 找不到 dylib | 开发包检查 Homebrew 依赖；Release 包重新运行 bundler 和 `verify-bundle.sh`，不能直接复制整个 Homebrew 前缀 |

## 八、交付前检查清单

### Linux

- [ ] 普通用户完成 Release 构建。
- [ ] `deploy/install.sh` 或审核过的 AUR 包完成安装。
- [ ] `guardd-users` 组和登录会话已刷新。
- [ ] 已审核 `guardctl setup --home` 生成的配置。
- [ ] `strict-filesystem`、systemd、polkit、user helper 状态正常。
- [ ] `guardctl status` 为真实 `ACTIVE`，无 mark/classifier/queue/audit 错误。

### macOS

- [ ] 开发包与 Release 包没有混用。
- [ ] Release 包无 Homebrew 绝对运行时依赖，nested signing 显式完成。
- [ ] 正式路径 profile、entitlement、Team ID、hardened runtime 均验证。
- [ ] notarize/staple/Gatekeeper 通过，或明确记录为 BLOCKED。
- [ ] App 安装在 `/Applications`，extension 已批准，XPC/ES/FDA health 正常。
- [ ] 只用临时 profile/key 完成浏览器、SSH、namespace 验收。
- [ ] 更新、diagnose、uninstall dry-run 完成，未触碰用户源数据。
