# 构建与部署手册

本文是当前仓库唯一的构建和部署主教程。命令默认从仓库根目录执行。Linux 与 macOS 是两个独立流程；本项目不需要 Docker。

## 通用准备

不要把真实浏览器 profile、Cookie、密码、session token 或 SSH 私钥用于测试。所有验收使用合成 fixture 和临时目录。普通用户完成编译，只有安装系统服务或写入 `/Applications` 时才提权，不要用 `sudo cargo build`。

```sh
git clone https://github.com/PLFJY/sensitive-file-guard.git
cd sensitive-file-guard
cargo fmt --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
cargo build --release
git diff --check
```

Linux 与 macOS 平台实现已按 target 隔离：反平台 crate 只编译为空边界，`guardd` 在非 Linux 平台只返回 unsupported。上述 workspace 检查应在两个原生平台都执行并通过；fanotify、Endpoint Security、系统扩展和权限验收仍需在对应平台运行。

## 一键脚本

### Linux

脚本先以当前用户执行 `cargo build --release`，再调用 `deploy/install.sh` 安装二进制、systemd、polkit 和桌面文件；只有在没有 `/etc/guardd/config.json` 时才调用 `guardctl setup`，绝不覆盖现有配置。

```sh
scripts/build-deploy-linux.sh
scripts/build-deploy-linux.sh --build-only
scripts/build-deploy-linux.sh --no-start
scripts/build-deploy-linux.sh --yes
```

状态检查：`sudo systemctl status guardd`、`systemctl --user status guard-notify`、`guardctl status`。卸载：`sudo deploy/install.sh --uninstall`。首次加入 `guardd-users` 后可能需要注销并重新登录。

### macOS 自用包

当前 macOS 目标是自用/实验路径：SIP 关闭、本地证书、System Extension developer mode、用户手动批准完全磁盘访问。脚本不会自动关闭 SIP、修改 TCC、自动激活系统扩展，也不会读取受保护文件。

```sh
scripts/macos/build-deploy-self-use.sh
```

脚本会检查 SIP，创建或复用本机 Keychain 身份，构建并验证 `SELF_USE_SIP_OFF=1` 包，把已安装的 `/Applications/Sensitive File Guard.app` 和遗留 `/Applications/Guard.app` 可恢复地移入废纸篓，安装新包并注册可选通知 helper。部署后手动执行 `sudo systemextensionsctl developer on`，再打开 Sensitive File Guard，在 Protection 页面安装扩展和批准完全磁盘访问。

以下命令只在临时目录创建合成 app bundle，验证两种旧包都会被移到可恢复备份、新包会安装到目标路径；不会构建、签名或访问 `/Applications`：

```sh
scripts/macos/build-deploy-self-use.sh --test-legacy-migration
```

## Linux 手工流程

Arch 依赖示例：

```sh
sudo pacman -S --needed base-devel cargo rust git pkgconf gtk4 libadwaita systemd polkit
```

Debian/Ubuntu 安装 `build-essential cargo rustc git pkg-config libgtk-4-dev libadwaita-1-dev systemd polkitd`；Fedora 安装对应的 `gcc make cargo rust gtk4-devel libadwaita-devel`。

```sh
cargo build --release
sudo deploy/install.sh
sudo /usr/local/bin/guardctl setup --home "$HOME"
sudo systemctl enable --now guardd
systemctl --user daemon-reload
systemctl --user enable --now guard-notify
guardctl status
```

`setup` 会显示待写入的严格配置并要求人工确认。不要创建空的 `/etc/guardd/config.json`；空配置意味着没有受保护资源。

## macOS 手工流程

先在 SIP 开启状态创建身份，再构建和验证：

```sh
scripts/macos/create-self-use-signing-identity.sh
SELF_USE_SIP_OFF=1 CODESIGN_TIMESTAMP=none scripts/macos/build-release-app.sh
VERIFY_SIGNING_MODE=self-use scripts/macos/verify-bundle.sh build/macos-release/Sensitive File Guard.app
```

私钥只进本机 Keychain。如果出现“codesign wants to use GuardSelfUse keychain”，使用该专用 Keychain 的生成密码，不是 macOS 登录密码；无法解锁时保留旧 keychain，改用新的明确路径。`LOCAL_SIGNING_ONLY=1` 只是无 entitlement 的打包 smoke test，不能真实拦截。

确认离线检查通过后，重启进入 macOS Recovery，手动执行 `csrutil disable`，重启回系统后运行：

```sh
csrutil status
sudo systemextensionsctl developer on
open build/macos-release/Sensitive File Guard.app
```

GUI 安装扩展后，必须同时看到生命周期 API、`systemextensionsctl list`、`guard-es` 运行和 authenticated XPC 健康；完全磁盘访问由用户在系统设置中批准，Guard 不改 TCC 数据库。

## 升级、回滚和排错

Linux 重新构建后再次执行安装脚本，已有配置会保留。macOS 一键脚本将旧包放入废纸篓，确认新包正常后再手动清理备份。不要用 `rm -rf` 删除不确定的系统扩展或 app；先用 `systemextensionsctl list` 和 `scripts/macos/diagnose.sh` 记录状态。

- `the application cannot be opened`：确认打开的是 `Sensitive File Guard.app` 而不是 zip，并运行 `verify-bundle.sh`。
- `Pending Authorization Helper`：只是显示待处理确认的可选 helper，不拥有防护扩展。
- `NOT_ENTITLED`：从最终包检查 entitlement，不能用 provisioning 缺失笼统解释。
- Linux 服务失败：检查 `/etc/guardd/config.json` 是否存在且非空，再查看 `journalctl -u guardd`。

macOS 阶段报告统一放在 `reports/mac/`，记录 BASE HEAD、构建模式、entitlement、测试命令、通过项和阻塞项。
